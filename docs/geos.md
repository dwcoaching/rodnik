# GEOS для PHP без Docker

Чтобы проверять вхождение координаты в полигон через GEOS из PHP, нужны два отдельных компонента: системная библиотека **GEOS** (`libgeos`) и PHP-расширение **`geos.so`** (`ext-geos`). Установка `libgeos-dev` или `brew install geos` сама по себе не добавляет расширение в PHP.

В корне проекта находятся два установщика:

| Скрипт | Окружение |
| --- | --- |
| [`install-geos-server.sh`](../install-geos-server.sh) | Ubuntu 24.04, PHP 8.5 CLI/FPM, запуск от root |
| [`install-geos-local.sh`](../install-geos-local.sh) | macOS, Laravel Herd с PHP 8.5, Homebrew, запуск от обычного пользователя |

Установка расширения не переводит приложение на GEOS. Проверки координат по-прежнему выполняет [`GeoJsonArea`](../app/Library/GeoJsonArea.php); установщики не меняют PHP-код, `composer.json` и `herd.yml`.

## Версии и совместимость

При обследовании 6 сентября 2026 года окружения выглядели так; это исходное состояние, а не результат установки:

| Окружение | ОС / архитектура | PHP | GEOS |
| --- | --- | --- | --- |
| Локально | macOS / arm64 | Herd 8.5.5 CLI/FPM, Homebrew toolchain 8.5.7 | Библиотека и расширение отсутствовали |
| `rodnik.today` | Ubuntu 24.04 / x86_64 | 8.5.7 CLI/FPM | Расширение отсутствовало |
| `ilya.rodnik.today` | Ubuntu 24.04 / x86_64 | 8.5.8 CLI/FPM | Расширение отсутствовало |

Скрипты используют один исходник `php-geos`, закреплённый по commit и SHA-256 архива:

```text
Commit: 889e2b1d9aa6f82995db4dab6891f48c3bacfb59
Archive: https://codeload.github.com/libgeos/php-geos/tar.gz/889e2b1d9aa6f82995db4dab6891f48c3bacfb59
SHA-256: c20ab4c6c0b2c27f8fee06191d623c76df696907267e78aeee12c7bbbe66b7af
```

В этот commit входит [исправление для PHP 8.5](https://github.com/libgeos/php-geos/commit/15ab5aaf541230ea0d81525887d9b496285f5e9c). В [конфигурации upstream CI](https://github.com/libgeos/php-geos/blob/889e2b1d9aa6f82995db4dab6891f48c3bacfb59/.woodpecker/ci.yml) присутствуют PHP 8.5.6 и GEOS 3.10–3.14. Наличие CI-матрицы не заменяет проверку сборки на конкретной машине.

Системная библиотека берётся из пакетного менеджера ОС. На обследованных серверах доступен `libgeos-dev` 3.12.1; Homebrew может предоставлять более новую версию. Таким образом, унифицирован исходник PHP-расширения и способ проверки, но версии `libgeos` на macOS и Ubuntu могут различаться.

Бинарник собирается отдельно на каждой платформе. Нельзя переносить `geos.so` между macOS и Linux или между arm64 и x86_64. Кроме архитектуры должны совпадать PHP module API, NTS/ZTS и режим debug. У текущего PHP 8.5 module API — `20250925`. Расширение использует [стабильный GEOS C API](https://github.com/libgeos/geos#using-the-c-interface); это не отменяет зависимости от ABI самого PHP.

В Ubuntu 24.04 обычный пакет `php-geos` привязан к PHP 8.3, поэтому установщик собирает расширение для PHP 8.5. Он не подключает репозитории другого выпуска Ubuntu и не устанавливает `php-geos` через APT.

## Режимы запуска

Без аргументов или с `--plan` оба скрипта печатают план и завершаются: пакеты, конфигурация и сервисы не меняются. План описывает действия, но не проверяет готовность текущей машины к установке. `--help` выводит справку. Только `--execute` запускает установку.

```bash
bash ./install-geos-server.sh
bash ./install-geos-server.sh --plan
bash ./install-geos-server.sh --help
bash ./install-geos-local.sh
bash ./install-geos-local.sh --help
```

`--execute` разрешает скачивание исходников, установку зависимостей, сборку, подключение расширения и перезапуск соответствующих сервисов. APT/Homebrew могут обновить зависимости, включая пакеты PHP для сборки. Эти действия выполняют при подготовке окружения или обновлении расширения, а не при каждом deploy приложения.

## Сервер: Laravel Forge

Предпочтительный способ — отдельный [Forge Recipe](https://laravel.com/forge/docs/recipes) с пользователем **root**. В Forge откройте **Recipes → New recipe**, задайте имя, выберите `root` и добавьте вызов установщика. Скрипт должен уже присутствовать в проверенном checkout на выбранном сервере:

```bash
bash /home/rodnik/rodnik.today/install-geos-server.sh --execute
```

Для тестового сервера используйте его путь:

```bash
bash /home/ilya/ilya.rodnik.today/install-geos-server.sh --execute
```

Проверьте абсолютный путь к checkout в настройках сайта Forge, особенно при использовании releases/current. Сначала выполните Recipe на тестовом сервере и проверьте журнал, затем отдельно на production. Для просмотра плана удалите `--execute`.

Серверный скрипт автономный: его можно передать через stdin или сохранить целиком в Recipe без остальных файлов проекта. Если вставляете сам текст файла в Recipe, добавьте перед ним строку `set -- --execute`: она передаёт аргумент установщику. Без неё будет выведен только план. Не используйте `source` для подключения установщика в другой скрипт.

### Запуск через SSH

Из корня локального checkout можно передать скрипт без копирования в репозиторий на сервере:

```bash
ssh -l ilya ilya.rodnik.today 'sudo -n bash -s -- --execute' < ./install-geos-server.sh
```

После проверки тестового окружения:

```bash
ssh -l rodnik rodnik.today 'sudo -n bash -s -- --execute' < ./install-geos-server.sh
```

Эти команды требуют уже настроенного права запускать Bash от root без пароля. `sudo -n` завершится ошибкой, если такого права нет. У [изолированных пользователей Forge](https://laravel.com/forge/docs/sites/user-isolation) sudo обычно ограничен; в этом случае используйте Recipe от root. Установщик сам не меняет sudoers.

Серверный установщик проверяет Ubuntu 24.04 и PHP 8.5, устанавливает зависимости через APT, собирает закреплённый исходник подходящими `phpize`/`php-config` и включает расширение для PHP 8.5 CLI/FPM. Перед сообщением об успехе выполняются проверки собранного модуля и подключённой конфигурации.

Каждая новая сборка хранится в отдельном каталоге `/usr/lib/php/20250925/rodnik-geos/<commit>/build.XXXXXXXX/`; уже загруженный `geos.so` не перезаписывается. Настройка находится в `/etc/php/8.5/mods-available/rodnik-geos.ini`, ссылки — в `cli/conf.d/20-rodnik-geos.ini` и `fpm/conf.d/20-rodnik-geos.ini`. Обнаружив чужое подключение GEOS или дубликаты, скрипт останавливается до установки пакетов, чтобы не смешивать конфигурации.

Установщик проверяет конфигурацию `php-fpm8.5 -t` до установки пакетов и после подключения расширения. После успешных проверок он делает reload активного `php8.5-fpm`; остановленный PHP-FPM сам не запускает. Скрипты устанавливаемых APT-пакетов могут отдельно обновить или перезапустить PHP.

Если ошибка возникла после начала активации, установщик восстанавливает прежний управляемый INI и удаляет только созданные им при этом запуске ссылки CLI/FPM. Установленные пакеты и новые модули сохраняются. Если reload уже был вызван, проверьте `php-fpm8.5 -t` и вручную выполните reload восстановленной конфигурации: второй reload автоматически не запускается. При ошибке самого восстановления резервная копия сохраняется, а её путь выводится в журнал.

PHP-FPM и консольные процессы загружают расширения отдельно. После установки перезапустите долгоживущие процессы очередей и `tiles:daemon` через существующий механизм Forge; новый CLI-процесс загрузит расширение автоматически. Для обычных Laravel workers в deployment script используется `$FORGE_PHP artisan queue:restart`, для Horizon — `$FORGE_PHP artisan horizon:terminate`. Проверьте, что у workers выбран PHP 8.5. [Документация Forge по очередям](https://laravel.com/forge/docs/sites/queues).

## Локально: Laravel Herd

Нужны установленный Herd, Homebrew и инструменты сборки macOS. Запускайте из корня этого проекта от обычного пользователя:

```bash
bash ./install-geos-local.sh --execute
```

Скрипт определяет PHP текущего сайта через `herd which-php` и требует PHP 8.5 NTS. Значение в `herd.yml` при обследовании было `8.4`, хотя фактически Herd использовал PHP 8.5; скрипт ориентируется на работающий Herd и не переписывает настройки сайта.

Через Homebrew устанавливаются `php@8.5` для сборки, `geos`, `autoconf` и `pkgconf`. PHP от Homebrew используется как toolchain, а приложение продолжает работать на Herd. Это соответствует [способу установки дополнительных расширений, описанному Herd](https://herd.laravel.com/docs/macos/technology/php-extensions).

Модуль хранится вне Homebrew Cellar, в отдельном каталоге `~/Library/Application Support/Herd/config/php/85/rodnik-geos/<commit>.XXXXXX/geos.so`. Поэтому очистка старых Homebrew PHP-пакетов не удаляет сам `geos.so`; при этом его зависимость от Homebrew GEOS сохраняется. Для загрузки используется отдельный `99-rodnik-geos.ini` в конфигурации Herd PHP 8.5, основной `php.ini` не дополняется повторяющимися строками.

После проверки модуля и конфигурации PHP-FPM с явным путём к `Herd/config/fpm/8.5-fpm.conf` скрипт выполняет `herd restart`. Этот перезапуск нужен, чтобы HTTP-запросы использовали новую конфигурацию; он затрагивает сервисы Herd и другие локальные сайты. [Документация Herd по PHP settings](https://herd.laravel.com/docs/macos/technology/php-settings).

Если старая версия установщика завершилась сообщением `GEOS did not load in Herd PHP-FPM` после успешных геометрических проверок, обновите скрипт и повторите запуск с `--execute`. Причиной мог быть канал `php-fpm -m | grep -q`: `grep` завершался после первого совпадения, PHP-FPM получал ошибку записи, а `pipefail` запускал откат INI. Исправленные установщики полностью считывают вывод FPM и проверяют код завершения до поиска расширения. Удалять установленные зависимости для повторного запуска не нужно.

Если установка завершилась ошибкой после изменения INI, локальный скрипт восстанавливает предыдущий управляемый INI или удаляет только что созданный. Установленные зависимости и собранные модули сохраняются. Если ошибка произошла при перезапуске Herd, проверьте его состояние и перезапустите после проверки восстановленной конфигурации.

## Проверки и повторная установка

Установщики проверяют загрузку кандидата до включения и проверяют подключённое расширение перед сообщением об успехе. Геометрические smoke checks охватывают точки внутри и снаружи полигона, внешнюю границу, отверстие, границу отверстия и `MultiPolygon`. Также проверяются загрузка расширения в PHP-FPM и его конфигурация. Это проверка работоспособности установленного расширения, а не полный тестовый набор upstream и не тест миграции приложения на GEOS.

Повторный запуск не добавляет дубликаты конфигурации. Серверный скрипт может переиспользовать уже установленный им модуль того же commit, если проверки проходят; в этом случае он не запускает APT и сборку. Локальный скрипт каждый раз собирает новый модуль в отдельном каталоге и переключает управляемый INI на него. Старые каталоги сборок автоматически не удаляются.

При изменении PHP minor-версии, например 8.5 → 8.6, нужны проверка совместимости исходника и отдельная сборка: текущие скрипты рассчитаны на PHP 8.5 и не переключают версию автоматически. После обновления системной GEOS повторно проверьте загрузку и геометрические результаты.

Дополнительная ручная проверка после установки:

```bash
# Локально, в корне проекта
herd php --ri geos
herd php -r 'echo GEOSVersion(), PHP_EOL;'

# На сервере
php8.5 --ri geos
php8.5 -r 'echo GEOSVersion(), PHP_EOL;'
```

Эти команды проверяют CLI. Успех CLI сам по себе не доказывает, что уже запущенные PHP-FPM или workers загрузили ту же конфигурацию.

## Вхождение точки и границы полигона

При последующем переходе приложения на GEOS нужно отдельно выбрать семантику границ. Для одного валидного полигона с отверстием:

| Положение точки | GEOS `contains()` | GEOS `covers()` | Текущий `GeoJsonArea::contains()` |
| --- | --- | --- | --- |
| Внутри полигона, вне отверстия | `true` | `true` | `true` |
| На внешней границе | `false` | `true` | `true` |
| Внутри отверстия | `false` | `false` | `false` |
| На границе отверстия | `false` | `true` | `false` |
| Снаружи полигона | `false` | `false` | `false` |

Существующая реализация также использует допуск `EPSILON` при проверке отрезка. Поэтому ни `contains()`, ни `covers()` не являются прямой заменой без изменения поведения. Определения операций приведены в документации [ST_Contains](https://postgis.net/docs/ST_Contains.html) и [ST_Covers](https://postgis.net/docs/ST_Covers.html), выполняемых GEOS.

Координаты передаются в порядке **долгота, широта** (`x, y`), как в [GeoJSON RFC 7946](https://datatracker.ietf.org/doc/html/rfc7946#section-3.1.1). GEOS работает на плоскости, не выполняет геодезические вычисления на эллипсоиде и не исправляет пересечение антимеридиана автоматически. Для мировых полигонов и некорректных колец это отдельная задача подготовки данных. [GEOS FAQ](https://libgeos.org/usage/faq/).
